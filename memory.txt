## 2026-02-02 - 重构：Observatory 独立部署

### 需求
用户要求将 Observatory 从 Control Plane Server 中分离出来，作为独立进程部署。

### 重构前架构
```
control_plane_server (单进程)
    ├── ControlPlane (gRPC: 50051)
    └── Observatory (HTTP: 8080) ← 内嵌
```

### 重构后架构
```
┌─────────────────┐        ┌─────────────────────────────────────┐
│   Observatory   │  gRPC  │         Control Plane               │
│  (独立进程)      │◄──────►│         (独立进程)                   │
│                 │        │                                     │
│  HTTP: 8080     │        │  gRPC: 50051                        │
│  - Web UI       │        │  - Task Management                  │
│  - REST API     │        │  - Worker Management                │
└─────────────────┘        └─────────────────────────────────────┘
         │
         ▼
    Web Browser
```

### 修改的文件

#### 1. observatory.h - 完全重写
- 移除对 `ControlPlane*` 的直接依赖
- 添加 gRPC 客户端配置 (`control_plane_address`, `grpc_timeout_ms`, `reconnect_interval_sec`)
- 添加连接管理 (`ConnectLoop()`, `TryConnect()`, `IsConnected()`)
- 添加连接状态 API (`HandleApiConnectionStatus()`)

#### 2. observatory.cc - 完全重写
- 实现 gRPC 客户端自动连接/重连
- 所有数据获取通过 gRPC stub 调用 Control Plane
- 前端 HTML 添加连接状态指示器和断连提示

#### 3. observatory_server.cc - 新增
- 独立的 Observatory 服务器入口
- 命令行参数：
  - `-c <address>`: Control Plane 地址 (默认: localhost:50051)
  - `-p <port>`: HTTP 端口 (默认: 8080)
  - `-b <address>`: HTTP 绑定地址 (默认: 0.0.0.0)
  - `-t <ms>`: gRPC 超时 (默认: 5000ms)
  - `-r <sec>`: 重连间隔 (默认: 5s)

#### 4. control_plane_server.cc - 简化
- 移除 Observatory 相关代码
- 移除 `-w` 参数

#### 5. control_plane.cc - 添加 Observatory gRPC API 实现
- `ListTasks()` - 获取任务列表
- `GetMetricsSnapshot()` - 获取实时指标快照
- `GetWorkerDetail()` - 获取 Worker 详情

#### 6. CMakeLists.txt - 重新组织
```cmake
# Control Plane 核心库 (不含 observatory)
add_library(control_plane_core STATIC ...)

# Control Plane Server
add_executable(control_plane_server ...)

# Observatory 库 (独立 gRPC 客户端)
add_library(observatory STATIC observatory.cc)

# Observatory Server (独立部署)
add_executable(observatory_server observatory_server.cc)
```

### 使用方式

```bash
# 1. 启动 Control Plane Server
./control_plane_server -l 0.0.0.0:50051

# 2. 启动 Observatory Server (可以在另一台机器)
./observatory_server -c localhost:50051 -p 8080

# 3. 访问监控界面
open http://localhost:8080
```

### 优势
1. **独立扩展** - Observatory 可以独立部署多个实例
2. **灵活部署** - 可以部署在不同机器上
3. **故障隔离** - Observatory 故障不影响 Control Plane
4. **多监控** - 一个 Observatory 可以监控多个 Control Plane（未来扩展）

### 前端变化
- 添加连接状态指示器 (Connected/Disconnected)
- 断连时显示重连提示遮罩
- API 响应包含 `connected` 字段

## 2026-02-02 - Q&A：Observatory 是否独立存在？

**问题**：这个观测平面是独立存在的吗？

**答案**：**不是独立存在的**，Observatory 是内嵌在 Control Plane Server 中的组件。

**架构关系**：
```
control_plane_server (进程)
    ├── ControlPlane (gRPC 服务, 端口 50051)
    │   ├── WorkerManager
    │   ├── TaskScheduler
    │   └── gRPC Service
    └── Observatory (HTTP 服务, 端口 8080) ← 内嵌组件
        ├── 实时指标采集线程
        ├── HTTP 服务器
        └── 内嵌前端 HTML/JS
```

**关键设计**：
- `Observatory` 持有 `ControlPlane*` 指针（不拥有所有权）
- 直接调用 ControlPlane 的方法获取数据
- 随 control_plane_server 一起启动/停止

**启动命令**：
```bash
./control_plane_server -l 0.0.0.0:50051 -w 8080
# gRPC: 50051, HTTP: 8080
```

**如果需要独立部署**，需要重构为通过 gRPC 客户端连接 Control Plane。

## 2026-02-02 - 重构：实现 CaaS-LSM 架构（Tendisplus → Control Plane → CSA Workers）

### 问题描述
原设计中 `compaction_service.cc` 直接连接 CSA Server（通过 `csa_address` 配置），
不符合 CaaS-LSM 架构的设计理念：
- 正确架构：Tendisplus → Control Plane → Multiple CSA Workers
- 错误实现：Tendisplus → CSA Workers（直连）

### 解决方案
重构代码支持两种模式：
1. **Control Plane 模式**（推荐）：通过 `ControlPlaneClient` 提交任务到控制平面
2. **Legacy 模式**（兼容）：直连 CSA Server（用于单节点测试）

### 修改的文件

1. **server_params.h** - 添加 `controlPlaneAddress` 配置
```cpp
std::string controlPlaneAddress = "";  // Control Plane address (host:port)
```

2. **server_params.cpp** - 注册配置参数
```cpp
REGISTER_VARS_DIFF_NAME("control_plane_address", controlPlaneAddress);
```

3. **def.h** - 添加 `control_plane_address` 到 `RemoteOpenAndCompactOptions`
```cpp
std::string control_plane_address;  // CaaS-LSM: Control Plane address
std::string csa_address;            // Legacy: Direct CSA address
```

4. **compaction_service.h** - 重构接口
   - 添加 `use_control_plane_` 标志
   - 添加 `control_plane_client_` 成员
   - 添加 `InitControlPlaneClient()` 方法
   - 添加 `WaitForCompleteViaControlPlane()` 方法
   - 添加 `WaitForCompleteViaDirectCSA()` 方法
   - 添加 `IsUsingControlPlane()` 方法

5. **compaction_service.cc** - 核心重构
   - `InitRemoteCompaction()` 根据配置选择模式
   - `InitControlPlaneClient()` 初始化控制平面客户端
   - `WaitForCompleteV2()` 分发到对应模式
   - `WaitForCompleteViaControlPlane()` 通过控制平面提交任务
   - `WaitForCompleteViaDirectCSA()` 保留原有直连逻辑

6. **rocks_kvstore.cpp** - 传递配置
   - 优先读取 `controlPlaneAddress`
   - 回退到 `csaAddress`

7. **tendisplus_rc.conf** - 配置示例
   - `control_plane_address` 替代 `csa_address`
   - 添加架构说明

### 架构图
```
┌─────────────┐      ┌─────────────────┐      ┌─────────────┐
│ Tendisplus  │─────▶│  Control Plane  │─────▶│ CSA Worker1 │
│   Node 1    │      │   (Scheduler)   │      ├─────────────┤
├─────────────┤      │                 │─────▶│ CSA Worker2 │
│ Tendisplus  │─────▶│ - Task Queue    │      ├─────────────┤
│   Node 2    │      │ - Load Balance  │─────▶│ CSA Worker3 │
└─────────────┘      │ - Worker Mgmt   │      └─────────────┘
                     └─────────────────┘
                            ▲
                            │ Shared Storage (NFS/HDFS/S3)
                            ▼
```

### 工作流程
1. Tendisplus 启动时检查 `control_plane_address`
2. 如果配置了控制平面：
   - 创建 `ControlPlaneClient`
   - 连接控制平面
   - 通过 `SubmitCompactionTask()` 提交任务
   - 通过 `WaitForTaskResult()` 等待结果
3. 如果未配置控制平面，回退到 Legacy 模式（直连 CSA）

### 配置示例
```conf
# CaaS-LSM 架构（推荐）
control_plane_address localhost:9010
remote_compaction.shared_fs_uri nfs://localhost/shared/rocksdb

# Legacy 模式（单节点测试）
# csa_address localhost:8010
```

## 2026-02-01 - 修复链接错误：重构共享文件系统接口设计

### 问题描述
编译时出现链接错误：
```
undefined reference to `rocksdb::NFSFileSystem::Create`
undefined reference to `rocksdb::NewNFSFileSystem`
undefined reference to `rocksdb::CreateSharedFileSystem`
undefined reference to `rocksdb::RegisterSharedFileSystemPathPrefix`
```

### 问题根源
`rocks_kvstore.cpp` 直接调用了 NFS 具体实现（`NFSFileSystem::Create`、`NewNFSFileSystem`），
而不是使用统一的共享文件系统接口 `CreateSharedFileSystem`。

这违反了接口抽象原则：上层代码不应该依赖具体实现。

### 解决方案
重构设计，让 `rocks_kvstore.cpp` 只使用统一接口：

**修改前**（错误的设计）:
```cpp
// rocks_kvstore.cpp 直接判断协议类型，调用具体实现
if (shared_fs_uri.find("nfs://") == 0) {
    rocksdb::NFSFileSystem::Create(...);  // 直接依赖NFS实现
    rocksdb::NewNFSFileSystem(...);       // 直接依赖NFS实现
} else {
    rocksdb::CreateSharedFileSystem(...); // 只有非NFS才用统一接口
}
```

**修改后**（正确的设计）:
```cpp
// rocks_kvstore.cpp 只使用统一接口
rocksdb::CreateSharedFileSystem(base, uri, local_prefix, &result);
// CreateSharedFileSystem 内部处理不同协议
```

### 修改的文件

1. **shared_filesystem.h** - 更新接口签名，添加 `local_prefix` 参数
2. **shared_filesystem.cc** - 实现内部根据 URI 协议调用具体实现（NFS支持URI模式和路径匹配模式）
3. **rocks_kvstore.cpp** - 移除对 `nfs_filesystem.h` 的依赖，只使用统一接口

### CMakeLists.txt 库结构调整

用户要求将 shared_filesystem 单独设置为静态库：

**修改后的库依赖结构**:
```
rocks_kvstore
    ↓ 链接
shared_fs (新增独立静态库，包含 shared_filesystem.cc)
    ↓ 链接
nfs_fs (NFS 具体实现：nfs_filesystem.cc + nfs_file.cc)
```

**CMakeLists.txt 修改**:
```cmake
# NFS 具体实现库
add_library(nfs_fs STATIC nfs_filesystem.cc nfs_file.cc)

# 共享文件系统接口层（独立静态库）
add_library(shared_fs STATIC shared_filesystem.cc)
target_link_libraries(shared_fs PUBLIC nfs_fs rocksdb)

# rocks_kvstore 链接 shared_fs
target_link_libraries(rocks_kvstore ... shared_fs ...)
```

### 设计原则
```
┌─────────────────────────────────────────────────────────────┐
│                    rocks_kvstore.cpp                        │
│                         (上层)                              │
│                           │                                 │
│                           ▼                                 │
│              CreateSharedFileSystem()                       │
│                    (统一接口)                                │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                      shared_fs 库                           │
│                  shared_filesystem.cc                       │
│                      (接口层)                                │
│                           │                                 │
│         ┌─────────────────┼─────────────────┐              │
│         ▼                 ▼                 ▼              │
│   nfs://             hdfs://            s3://              │
│   NFSFileSystem      HdfsFileSystem     S3FileSystem       │
│     (具体实现)          (具体实现)         (具体实现)          │
└─────────────────────────────────────────────────────────────┘
```

### 职责分离
- `rocks_kvstore` - 只知道统一接口 `CreateSharedFileSystem`
- `shared_fs` - 接口层，负责路由到具体实现
- `nfs_fs` - NFS 具体实现

## 2026-03-22 - Bulk Load 可行性评估与设计文档

### 问题
用户要求参考 TendisPlus 现有存储层和迁移机制，评估远程 Bulk Load 的可行性，并给出设计文档和论文标题呼应性分析。

### 关键发现

#### TendisPlus 现有 Bulk Load 能力：完全空白
- TendisPlus 代码中**未使用** `SstFileWriter`、`IngestExternalFile` 等 RocksDB Bulk Load API
- 现有数据迁移（Migrate）使用**逐条 KV 事务写入**，效率低下
- RocksDB 层完整 Bulk Load API 可用（SstFileWriter + IngestExternalFile）
- `RocksKVStore::getBaseDB()` 暴露底层 `rocksdb::DB*`，可直接调用注入 API
- `getDataColumnFamilyHandle()` 可获取目标 CF 句柄

#### 可行性结论：✅ 高度可行
